# Potatobot — грабли и регрессия

Файл лежит рядом с кодом. После **любого** изменения проверяй одной командой:

```bash
cd /home/anton/potatobot && docker compose up -d --build
docker exec potatobot python3 /app/tests/suite.py     # 0 = всё ок, 1 = есть поломки
```

Набор проверяет 9 классов отказа (см.ниже). Он же ловит регрессии: дважды находил
поломку, внесённую мной же в том же заходе.

---

## 1. БД: float4 в колонках времени — молча ломает кулдаун

`REAL` в PostgreSQL — это float32. При unix-времени ~1.79e9 шаг дискретизации
**128 секунд**. `last_dig_time` округлялся вверх, `now - last_dig_time` уходил
в минус, guard `0 <= delta` не проходил — и кулдаун не срабатывал.

Симптом: игрок копал чаще раза в час, поведение «плавающее» (зависит от того,
в какую 128-секундную корзину попал момент копки).

```sql
SELECT round(extract(epoch from now())::real)::double precision
     - extract(epoch from now())::double precision;   -- +51.09 сек вперёд
```

Все колонки времени — `DOUBLE PRECISION`. Миграция `WIDEN_TIMESTAMP_COLUMNS`
в `init_database()` идемпотентна.

**Правило:** любая колонка с unix-временем — только float8.

## 2. Копка и бонус должны писаться одной транзакцией

Раньше: `update_user_dig()` (вес + счётчик) и `add_dig_record()` (история) —
два независимых автокоммита. Падение второго оставляло пользователю вес без
записи в истории, и статистика с историей расходились навсегда.

Сейчас `Database.dig_with_cooldown()` / `bonus_with_cooldown()`:
`UPDATE users ... RETURNING` + `INSERT в dig_history` в одной транзакции.

## 3. Кулдаун проверяется В SQL, а не до записи

Было: `SELECT` → проверка в Python → `UPDATE`. Два быстрых тапа успевали пройти
проверку до записи — кулдаун обходился.

Стало: условный `UPDATE ... WHERE last_dig_time IS NULL OR last_dig_time <= $3 - $4`.
Если ни одна строка не обновилась — срабатывает кулдаун.

**Проверка в наборе:** 5 одновременных `perform_dig()` → ровно 1 успех.

## 4. `parse_mode=HTML` ломается от любого `<`, `>`, `&`

Название и описание клана — свободный текст; `first_name` в Телеграме может
содержать `<`; описания ML-рекомендаций генерирует модель. Telegram отвергает
**всё сообщение** («can't parse entities»), юзер не видит ничего.

Всё пользовательское и модельное проходит через `escape_html()`.
Покрыто: имя и тег клана, описание клана, эхо описания при создании,
`first_name`, юзернеймы в топах, title/description рекомендаций, описания достижений.

**Правило:** в строку с `parse_mode="HTML"` любое значение не из кода — через `escape_html()`.

## 5. CancellableError вместо нормального текста

`dig_handler` перехватывал **любое** исключение и отвечал «💥 Ошибка при копке» —
включая штатный кулдаун. Для этого уже есть человеческий текст с таймером.

`CooldownError` и `ValidationError` теперь пробрасываются в middleware.

## 6. Middleware обязан отвечать и на CallbackQuery

Ошибки обрабатывались только при `isinstance(event, Message)`. При ошибке по
инлайн-кнопке не отвечали **вообще** — Telegram держал кнопку вечно
крутиться, пользователь не видел ничего.

Теперь `_tell(event, text)`: `CallbackQuery → event.answer(..., show_alert=True)`,
`Message → event.answer(...)`.

## 7. Необработанные словари растут по числу пользователей

`RateLimitMiddleware.requests` и `DailyBonusService._cache` чистились только
для текущего пользователя — для ушедших записи оставались навсегда.
Добавлены периодический свип и жёсткий предел кэша.

Таблица `sessions` тоже росла: `purge_expired_sessions()` существовал, но его
никто не вызывал. Теперь `CacheService.housekeeping()` подключён в `CleanupService`.

## 8. `REAL` vs `int` в asyncpg: нужен явный каст

```
total_kg = total_kg + $2
HINT: Could not choose a best candidate operator. You might need to add explicit type casts.
```

asyncpg не может вывести тип операнда у `+`. Нужен `$2::double precision`.
Этот дефект я внёс сам же в этом же заходе, и регрессионный набор его поймал.

**Правило:** любой float-плейсхолдер в SQL пиши с кастом.

## 9. Обрыв БД поднимал чужое исключение

При недоступной БД asyncpg бросает `ConnectionRefusedError` / `InterfaceError` /
`PostgresError`, а middleware ловит только `DatabaseError`. Итог: падение базы
показывалось пользователю как «💥 Произошла ошибка» и писалось в лог как
`unhandled_error`, хотя это не баг кода, а внешняя недоступность.

Теперь `Database.connect() / acquire() / transaction()` переводят всё это в
`DatabaseError`. Пользователь видит «🔧 Ошибка базы данных. Попробуй позже.»,
в лог попадает `database_error`.

**Проверка в наборе:** connect к мёртвому порту → `DatabaseError`.

Пул при этом восстанавливается сам: asyncpg выбрасывает мёртвые соединения и
переподключается — рестартить бота при кратковременном падении БД не нужно.

## 10. Веб-панель убрана целиком: `/api/v1` не проверял подпись

Решение владельца: админка нужна **только кнопками в Telegram**, без сайта.
Причина, по которой это правильно, а не просто вкус: `require_auth()` в
`app/web/routes.py` читал заголовок `X-Telegram-Init-Data` и доставал из него
Telegram ID **без проверки подписи** (в коде это было помечено «simplified»).
Любой мог подделать заголовок и читать чужую статистику, а `POST /api/v1/dig`
— копать от чужого имени.

Убрано: `app/web/admin.py`, `app/web/admin_auth.py`, `app/web/templates/`,
весь `/api/v1/*`, jinja2, `CacheService`, таблицы `sessions` и `counters`
(писались только панелью и API), `ADMIN_PANEL_URL`, `ADMIN_SESSION_SECRET`,
`LEADERBOARD_CACHE_TTL`.

Осталось ровно три HTTP-маршрута, и все они нужны: `/health` (его проверяет
Docker healthcheck и `potatobot_healthcheck.sh`), `/ready`, `/metrics`
(Prometheus). Проверка: все пути панели и API отдают 404.

## 11. Панель на кнопках: три ловушки, которые стоили прогона

**1. Клавиатура строилась в 13 местах, кнопка админа жила только в `/start`.**
Telegram заменяет клавиатуру целиком при каждом `reply_markup`, поэтому любой
ответ с «голой» `get_main_keyboard()` стирал ряд с админкой. Теперь функция
принимает `user_id` и сама добавляет ряд, а все 13 вызовов передают
`message.from_user.id` (в `daily_handler` параметр называется `event`).

**2. `except Exception: return False` в middleware молча отключал бан.**
`Database` не имела метода `fetchval`, поэтому первый вызов падал в
`except` — бан не работал бы вообще, а набор бы молчал. Добавлены
пасс-через-методы `fetchval/fetchrow/fetch/execute` и публичное свойство
`pool`. Общее правило: **проверка «исключение проглочено» обязана иметь
контрольный случай, где исключения нет.**

**3. Кэш бана 30 с делал разбан фиктивным.** `BanMiddleware` кэшировал флаг;
админ жал кнопку «Разбанить», а юзер ещё до 30 секунд оставался заглушенным.
Теперь кэш общий (`_BAN_CACHE`) и панель вызывает `forget_ban(tg_id)` сразу
после смены состояния. Набор проверяет разбан **через кнопку**, потому что
другого пути у админа нет: прямой `db.set_banned(..., False)` кэш не сбрасывает.

**Гард на кнопки пришлось расширить, а не подогнать под себя.** `adm:ban:` и
`adm:unban:` регистрируются через `F.data.startswith(("a","b"))`, а аудит
умел только одиночную строку — и объявил рабочие кнопки мёртвыми. Regex widened
на tuple-форму, и **добавлен контрольный тест на заведомо мёртвый callback**:
гард, который не может упасть, бесполезен.

## 12. Достижения: тост без записи

`get_user_achievements()` возвращал пустое множество с комментарием
«simplified version», поэтому `/achievements` показывал всё заблокированным
навсегда, а `check_achievements()` каждый раз радостно сообщал «Новое
достижение» — и никуда его не писал.

Теперь разблокировка пишется в `user_achievements` (таблица уже была),
читается оттуда же и не повторяется. Ошибки разблокировки глотаются:
косметика не должна ронять копку.

Важно: сервис работает с **внутренним** `users.user_id`, а не с Telegram ID
(`user_achievements.user_id` — внешний ключ на `users.user_id`).

## 12. Метрики были объявлены, но никогда не инкрементились

Объекты Prometheus лежали в `web/routes.py`, а сервисы, которые порождают
события, до них не могли дотянуться: `record_dig` и `record_daily_bonus` были
заглушками `pass`, DAU/WAU/MAU только логировались в `debug`.

Объекты вынесены в `app/metrics.py`, оттуда импортируют и экспортёр, и сервисы.

## 13. Мёртвые настройки

`ANTICHEAT_MAX_KG_PER_HOUR=50` при кулдауне 1 час и максимуме 7 кг недостижим:
физический потолок 7 кг/час. Теперь в `.env` явно 20.0 с комментарием — это
«второй эшелон», который срабатывает, если кулдаун когда-нибудь снизят.
Проверено: при обходе кулдауна кап срабатывает на 5-й копке.

## 14. `env_file` перечитывается только при пересоздании

`docker restart` переиспользует существующий контейнер и **не подхватывает
новые переменные из `.env`**. После правки `.env` нужен
`docker compose up -d --force-recreate <service>`. На этом молча остался
старое значение `ANTICHEAT_MAX_KG_PER_HOUR`.

## 15. Косметический обработчик не должен ронять игру

При неверном id разблокировка достижения давала `ForeignKeyViolationError`,
и вся копка падала. Обёрнул `unlock()` и `get_user_achievements()` в
try/except с предупреждением в лог.

## 16. Регрессионный набор не должен мусорить в БД

Первые версии `suite.py` создавали синтетических пользователей и не удаляли их
(хвост cleanup-а вызывал `fresh_user`, который создаёт, а не удаляет) — после
прогона в базе оставалось 107 юзеров.

Теперь cleanup один запрос: всё, у кого `tg_id <> admin_id`, удаляется
каскадно. Проверяйте после прогона: `SELECT count(*) FROM users` → 1.

## 18. Healthcheck 8 минут подряд перезапускал живой бот

`potatobot_healthcheck.sh` считал бот мёртвым по строке `Run polling` в логах.
aiogram пишет её **один раз при старте**, и никогда снова. Через 5 минут простоя
grep не находил ничего, три подряд FAIL → `docker restart` + алерт. Цикл
повторялся каждые ~8 минут, и в лог уходило «alert sent, state=alerted».

Проверено на живом: 19 строк `Run polling` на весь лог, все — из рестартов.

Вместо grep добавлен **heartbeat**: `app/services/heartbeat.py` пишет
`/tmp/potatobot.heartbeat` раз в 30 с из того же event loop, что и
`dp.start_polling()`. Крон спрашивает возраст файла через `docker exec`;
`MAX_BEAT_AGE=180` (три пропущенных записи). Это отвечает на исходный вопрос —
«жив ли event loop» — и заодно ловит зависший процесс, о котором grep молчал бы.

Проверка в обе стороны (обязательно, иначе «чисто» ничего не значит):
* 6 минут простоя на живом боте → **ноль** FAIL-строк;
* `HEARTBEAT_FILE=/tmp/not-a-real-file` → `no heartbeat file`;
* `MAX_BEAT_AGE=1` → `heartbeat stale by 13s`;
* `docker stop` → `container not running`;
* alert доставляемости — см. граблю 19.

## 19. «alert sent» в логе, когда токен был заглушкой

В задеплоенном скрипте стояло `TG_TOKEN="__TG_TOKEN__"` и
`CHAT_ID="__CHAT_ID__"` — задеплоен был шаблон, а не рабочая копия. `send_tg`
уводил вывод в `/dev/null 2>&1` и **всегда** писал «alert sent». По факту
`getMe` с заглушкой даёт 404, и ни одно уведомление не дошло.

Два вывода, оба про наблюдаемость:
1. Скрипт читает `BOT_TOKEN` и `ADMIN_USER_IDS` из `.env` в рантайме —
   подставлять нечего, секрет не лежит в коде.
2. `send_tg` возвращает код ответа и пишет `telegram: delivered` только при
   200; иначе `DELIVERY FAILED http=...` и состояние **не** переключается в
   `alerted`, чтобы попробовать снова. «Отправлено» больше не может быть
   написано при провале.

## 20. Гард, который читал собственную документацию

При установке healthcheck гард искал `__TG_TOKEN__` — и срабатывал на **моём же
комментарии**, где заглушка описана. Код был чистый, а установка отменялась.

Гард теперь вырезает комментарии (`grep -v '^[[:space:]]*#'`) и проверяет, что
присваивание `TG_TOKEN=`/`CHAT_ID=` является командной подстановкой, а не
строковым литералом. Правило: **гард обязан игнорировать комментарии** —
иначе следующий человек, который задокументирует проблему, получит ложную
тревогу и перестанет гарду верить.

## 21. `curl ... || echo 000` даёт `000000`

Когда curl падает, он всё равно печатает `000` через `-w`, и `|| echo "000"`
дописывает второй: в логе было `http=000000`. Мелочь в сообщении, но она
делала невозможным отличить «сервер не отвечает» от «скрипт сломан».

Правильно: присвоить вывод, и только если он пуст — подставить дефолт:
```sh
HTTP=$(curl -s -m 10 -o /dev/null -w '%{http_code}' "$HEALTH_URL" 2>/dev/null)
[ -n "$HTTP" ] || HTTP="000"
```

Ещё там же: `[ "$fails" -eq "$FAIL_THRESHOLD" ]` означало «перезапустить
ровно на третьем отказе». Если рестарт не помог, четвёртый отказ уже ничего не
делал. Нужно `-ge`.

## 22. Кнопка «открыть юзера» падала при первом же нажатии

`adm:u:<page>:<tg_id>` — четыре части через двоеточие, а код распаковывал их в
три: `_, page, tg = call.data.split(":")` → `ValueError: too many values to
unpack`. Настоящий баг, найденный в логах продакшена, когда владелец нажал
кнопку в панели.

**Аудит связности его не увидел:** он проверяет, что обработчик для `callback_data`
*существует*, а не что кнопка *работает*. 92 зелёные проверки это не поймали.

Теперь в наборе есть блок, который **нажимает** кнопки (`cq(...)` шлёт
callback_query) и читает ответ. Три грабли при написании этих проверок, все —
мои:

1. **Ассерт смотрел не туда.** Кнопки лежат в `reply_markup.inline_keyboard`, а
   я искал их в `text` сообщения. Лечится хелпером `kb_labels()`.
2. **`'Забанить' in labels` — это вхождение элемента, а не подстроки.**
   Элемент — `'🚫 Забанить'`. Ровно тот же класс, что `.warn`, найденный внутри
   `.msg.warn`, и `location /kolonka/`, удовлетворённый строкой `/sendRawTxt`.
3. **`touch -t` с хостовым временем внутри контейнера.** Хост в UTC+3,
   контейнер в UTC: «файл 15 минут назад» получил возраст **−9885 с**, тест
   проходил по остаточной строке лога, а не по своей. Тесты на возраст файла
   должны брать метку времени одинаково с обеих сторон.

Общее: **падающий тест надо чинить по напечатанному значению, а не по
предположению о том, что должно было вернуться.** Все три раза я писал
проверку «как мне кажется», а не «как это работает на самом деле».

## 23. Репозиторий без единого коммита за сутки работы

`Potatobot` был git-репозиторием с origin, но **75 изменений не были
закоммичены**, а `.gitignore` не существовал вообще — `.env` с токеном и
паролем БД стоял в untracked и был в одном `git add` от публикации.

Проверено до коммита: `git log --all --full-history -- .env` — никогда не
коммитился; перебор всех блобов `git grep -F <token>` и `<DATABASE_URL>` —
чисто. Добавлен `.gitignore` (`.env`, логи, бэкапы, `__pycache__`, `*.tar.gz`).

## 24. Push отклонён: параллельная сессия сделала ту же работу

`git push` вернул «rejected (fetch first)». На origin лежали два чужих коммита:
`8b80f21 Refactor: consolidate modules (~41 -> ~12 files)` и
`2c9b7b7 Remove stray draft files` — то есть **та же консолидация, сделанная
независимо**, параллельной сессией, с того же base `c592ed1`.

Прежде чем решать, сравнил их дерево со своим: там всё ещё `app/web/admin.py`
с шаблонами, в `routes.py` та же непроверенная подпись initData, в
`commands.py` — кнопка Web App, нет `escape_html` и нет ряда админки. Их версия
**строго старее** моей, переносить из неё было нечего.

Ребейз на их tip, все конфликты в мою сторону, с сохранением тега
`backup-before-rebase-20261006` до начала.

Две вещи из их работы **сохранил**, потому что выбросить их было бы неверно:
* явные `__init__.py` как маркеры пакетов (я сам их удалял как «мёртвые»);
* удалённые ими `app/utils/logging.py`, `validators.py`, `cache.py` — мой код их
импортирует, и ребейз удалил бы их, оставив `from app.utils.logging import
get_logger` без модуля.

А вот их `app/utils/__init__.py` с дублями всех четырёх модулей и
`import structlog` на уровне пакета — убрал: он превращал любой
`from app.utils.logging import ...` в скрытую зависимость от structlog.

## 25. requirements.txt врал о зависимостях

Проверил по факту импортов, а не по списку:

| пакет | использований | вердикт |
|---|---|---|
| `jinja2`, `aiohttp-jinja2` | 0 | только для шаблонов веб-панели |
| `aiohttp-session` | 0 | сессии удалённого Web App |
| `psycopg2-binary` | 0 | драйвер — `asyncpg` |
| `python-dotenv` | 0 | конфиг читает `pydantic-settings` |
| `redis` | 0 | сервис удалён, в файле остался комментарий-заголовок |

Плюс был комментарий `# Web App` с `aiohttp-session` под ним — «список
зависимостей» как источник правды о том, что боту нужно, не работает.

После обрезки: пересборка образа, `/health` `/ready` `/metrics` отвечают без
jinja2, набор 92/92. Правило: **зависимости проверяются grep по импортам, а не
глазами по requirements.**

## Итог сессии: два бага были не в коде, а в проверках

Правило, которое вытекает из всего вышеописанного: набор из 92 зелёных
проверок пропустил падение кнопки `adm:u:` и восемь минут рестартов живого
бота. И то и другое ловится только проверками, которые **действуют**, а не
которые есть:

* аудит связности доказывает, что обработчик существует; нажать кнопку он не
  может — нужен `cq()` и чтение `reply_markup`;
* healthcheck доказывал, что бот жив, проверяя в логе то, что пишется один
  раз; нужен сигнал от самого процесса (heartbeat);
* «alert sent» доказывало доставку, не спрашивая Telegram; нужен код ответа.

Отрисованная кнопка без обработчика — молчаливая поломка: юзер жмёт, ничего
не происходит. Набор сверяет всё, что бот рисует (`callback_data`,
`KeyboardButton`, `BotCommand`), с тем, что реально объявлено.

Нюанс: `dp.*.handlers` после `include_router` **пустой** — фильтры лежат в
роутерах. Проверять надо `commands_router.*.handlers` / `features_router.*.handlers`
или разбирать исходники. Плюс `F.data.startswith("clan_accept_")` не ловится
регексом по `F.data == "..."`.

## Чего НЕТ в наборе (и почему)

Инлайн-режим `@bot` и реальный HTTPS-вызов Telegram API проверяются
отдельными скриптами, а не этим набором: для инлайна нужен `InlineQuery`
с корректным `offset`, для сети — живой round-trip.

## Что набор уже проверяет

63 проверки, 15 классов: привязка кнопок, поведение экранов, правила копки,
атомарность под гонкой (5 и 20 одновременных копок), типы колонок, hostile
HTML, лимиты Telegram, тип исключений при обрыве БД, авторизация админки
(подпись, истёкший токен, пароль), достижения (разблокировка/повтор/устойчивость),
метрики (двигаются ли счётчики), античит (срабатывает ли кап), схема БД.

## Healthcheck

`potatobot_healthcheck.sh` раз в минуту из cron. Проверяет три признака:
контейнер жив, `/health` отвечает 200, в логах есть polling за 5 минут.
Три подряд провала → перезапуск + сообщение в Telegram; после восстановления —
ещё одно сообщение. Свой лог обрезается до 500 строк.

Важно: скрипт сам себя не перезапускает по таймауту cron, поэтому он должен
завершаться быстро (у него есть `timeout 10` на curl).

## Что делать при первом «FAIL»

1. Не откатывай — посмотри `detail`, там фактический ответ хендлера.
2. Проверь, что правка попала в **образ**, а не только в хост:
   `docker exec potatobot grep -n "<твоя правка>" /app/app/...`
3. Пересобери: `docker compose up -d --build`.
4. Прогони набор заново.
